# 智枢 ZhiHub 面试技术点总结

> 项目：智枢 ZhiHub -- 企业级多智能体客服与运营中枢系统
> 技术栈：Python 3.14 + FastAPI + LangGraph + litellm + PydanticAI + MCP（JSON-RPC 2.0）+ Milvus + Elasticsearch + Redis + MongoDB + MySQL + RabbitMQ
> 本文按"技术原理 → 代码位置 → 面试怎么说"结构组织，"面试怎么说"是口语化段落，面试时可直接说出来。

---

## 一、LangGraph 多智能体编排

### 技术原理
ZhiHub 用 LangGraph 把客服对话建模成一张状态图。核心是 `AgentState`（TypedDict）作为各节点共享的状态容器，`router` 是入口节点，做一次 LLM 调用同时产出意图、置信度、情绪、槽位四个信号；然后条件边 `_route_intent` 按优先级路由：愤怒情绪 > 敏感操作 > 低置信度 > 正常意图，分别导向知识问答、工单、订单、转人工四个 Agent 节点，各节点执行完直连 END。

项目用的是**同步 invoke 架构**而非异步流式，`graph.invoke(initial_state)` 一次跑完整条链路。好处是简单可调试、状态在内存里完整流转、出问题好定位；代价是延迟叠加（路由+检索+生成串行），但客服场景对单次延迟不敏感，换来了工程简单性。转人工没有用 LangGraph 原生的 `interrupt_before` + checkpoint 实现 true pause/resume，而是用 `should_interrupt` 同步标记 + agent_service 把会话置成 `waiting_human`--因为同步 invoke 架构不支持真正的中断恢复，同步标记在 demo 规模下能实现"暂停 AI、等坐席认领"的效果，且原理更易讲清。

条件边的优先级是业务逻辑决定的：愤怒情绪最高优先（愤怒用户让 AI 继续处理可能激化矛盾），敏感操作次之（退款等涉及资金必须人工），低置信度再次（避免误路由调错工具），最后才是正常意图分发。first-match 即返回，保证高优先级先判。

### 代码位置
- 状态定义：`app/agents/graph.py` 的 `AgentState(TypedDict)`
- 条件路由：`app/agents/graph.py` 的 `_route_intent()`
- 模式切换：`app/agents/graph.py` 的 `build_graph()` 读 `settings.agent_tool_mode` 切换 MCP/FC
- 入口驱动：`app/services/agent_service.py` 的 `handle_message()` 调 `graph.invoke()`
- 节点实现：`app/agents/nodes/*.py`

### 面试怎么说
"我们用 LangGraph 做多智能体编排，核心是一个 AgentState 状态图。router 节点一次 LLM 调用产出意图、置信度、情绪、槽位，条件边按优先级路由--愤怒情绪最优先转人工，然后敏感操作，再是低置信度，最后正常意图分发到知识、工单、订单三个 Agent。我特意用了同步 invoke 架构而不是异步流式，因为客服场景对单次延迟不敏感，同步架构状态流转完整、好调试，出问题能直接看到每步 state。转人工我没用 LangGraph 原生的 interrupt+checkpoint，而是用 should_interrupt 同步标记把会话置成 waiting_human 等坐席认领，因为同步架构不支持真正的中断恢复，这个简化在 demo 规模够用而且原理更好讲。条件边优先级是业务定的：愤怒用户必须先转人工安抚，否则 AI 处理可能激化矛盾。"

## 二、MCP 协议化工具调用

### 技术原理
ZhiHub 没有用官方 MCP SDK，而是手写了 JSON-RPC 2.0 协议信封。原因是官方 SDK 默认走 stdio 传输（子进程 stdin/stdout），而我们是 Web 服务架构，工具调用走 HTTP 更自然，手写信封剥离了 stdio 进程管理的复杂度，还能在面试里讲清协议长什么样。

信封三件套：请求 `{"jsonrpc":"2.0","id":...,"method":...,"params":{...}}`、成功 `{"jsonrpc":"2.0","id":...,"result":{...}}`、错误 `{"jsonrpc":"2.0","id":...,"error":{"code":...,"message":...}}`。错误码前 5 个（-32700~-32603）严格对齐 JSON-RPC 2.0 标准，后 2 个（-32000 权限拒绝、-32001 工具熔断）用规范允许的 -32xxx 业务扩展段。

`mcp_service.call_tool` 是唯一的工具调用入口，流程严格分层：解封信封 → 注入 tenant_id（覆盖客户端，防越权）→ 方法存在性校验 → 权限校验 → 熔断检查 → 入参校验 → 分发 server handler → 关键字段监控 → 封装成功信封。一个关键设计是**方法存在性校验在权限校验之前**：未知方法返回 -32601（标准语义）而非 -32000 权限拒绝，避免泄露"方法存在但无权"的信息。

### 代码位置
- 协议信封：`app/mcp_servers/base_server.py`（`build_request`/`build_success`/`build_error`/`parse_request`、错误码常量）
- 调用代理：`app/services/mcp_service.py` 的 `call_tool()`（分层校验 + 异常映射）
- 工单 Server：`app/mcp_servers/ticket_server.py`（`TICKET_TOOLS` inputSchema + `handle_ticket_tool` 分发）
- 订单 Server：`app/mcp_servers/order_server.py`
- HTTP 传输层：`app/api/v1/mcp/server.py`（tools/list + tools/call 端点）

### 面试怎么说
"工具调用我们走 MCP 协议，但没用官方 SDK，手写了 JSON-RPC 2.0 信封。因为官方 SDK 默认 stdio 传输，我们是 Web 服务走 HTTP 更合适，手写还能讲清协议细节。信封就是标准 JSON-RPC：请求带 method+params，成功带 result，错误带 error{code,message}，错误码前五个对齐标准，后两个 -32000 权限拒绝、-32001 熔断是业务扩展。call_tool 是唯一入口，分层校验：解封、注入 tenant_id、方法存在性、权限、熔断、入参、分发、监控。这里有个设计点--方法存在性校验放在权限校验前面，未知方法返回 -32601 而不是 -32000，避免攻击者通过权限错误探测出系统有哪些工具。整个流程把安全校验、熔断、监控都内聚在 call_tool 里，Agent 节点只管构造信封和解析响应。"

## 三、混合检索引擎

### 技术原理
这是全项目技术含量最高的单点。完整流程：查询改写（LLM 补全指代，"它怎么退款"→"XX订单怎么退款"）→ 双路召回（Milvus 向量 Top20 + ES BM25 Top20）→ RRF 融合 → bge-reranker 精排 Top5 → 置信度判断（Top1 < 0.6 触发 HyDE 兜底）→ 空知识库分支。

双路召回互补：向量召回抓语义相似（"退款"能召回到"退货款"），BM25 抓关键词精确匹配（工单号、专有名词）。融合用 **RRF（Reciprocal Rank Fusion）** 而非加权分数，因为两路分数尺度不同（向量是 IP 相似度 0~1，ES 是 BM25 score 可达几十），直接加权会被尺度大的那路主导；RRF 只看排名不看绝对分数，`score = Σ 1/(k+rank)`，k=60 是经验值，天然尺度无关。

精排用 bge-reranker 做交叉编码，比双塔召回精度高但慢，所以只对融合后候选精排。HyDE 兜底解决"查询与文档表述差异"--低置信度时让 LLM 生成假设回答文档，用它再去匹配知识库，召回率显著提升。

### 代码位置
- 主编排：`app/services/retrieval_service.py` 的 `hybrid_search()`
- 查询改写：`retrieval_service.py` 的 `rewrite_query()`
- 向量召回：`retrieval_service.py` 的 `vector_recall()`（Milvus IP + partition_key 租户隔离）
- BM25 召回：`retrieval_service.py` 的 `bm25_recall()`（ES + is_latest 过滤）
- RRF 融合：`retrieval_service.py` 的 `rrf_fuse()`
- HyDE 兜底：`retrieval_service.py` 的 `_hyde_retrieval()`
- Embedding + Collection：`app/core/embedding_client.py`（bge-m3 1024 维 + IVF_FLAT 索引）

### 面试怎么说
"检索引擎是项目技术含量最高的部分，做的是混合检索。先 LLM 改写查询补全指代，然后双路召回--Milvus 向量抓语义、ES BM25 抓关键词，两路各召回 Top20。融合用 RRF 不用加权分数，因为向量分数是 0 到 1、BM25 能到几十，尺度不同加权会被 BM25 主导；RRF 只看排名，score 等于各路排名倒数的和，天然尺度无关。融合后用 bge-reranker 交叉编码精排 Top5，比双塔召回准但慢所以只排候选。如果 Top1 置信度低于 0.6，触发 HyDE 兜底--让 LLM 生成一段假设回答，用假设回答的 embedding 再检索一次，解决用户问'怎么退款'但文档写'退款申请流程'的表述差异问题。全程降级，单路失败返回空让另一路兜底，不中断检索。"

## 四、Function Calling 对比

### 技术原理
ZhiHub 同时实现了 MCP 和 Function Calling 两种工具调用范式做对比（009 feature）。两者槽位收集、双因子校验、工具执行完全一致（FC 版复用 MCP 版的 phone 提取 helper，工具执行都走 `call_tool` 信封入口），唯一差异是"谁决定调工具"：

- **MCP 版**：Agent 代码在槽位齐全后**直接调** `call_tool`，Agent 决定调哪个工具、什么时候调。协议化、与 LLM 解耦、可审计、跨 LLM 通用。
- **FC 版**：把槽位喂给 LLM，传 `tools` 参数，**LLM 返回 tool_calls** 再由 Agent 执行。LLM 原生、简单但紧耦合特定 LLM 能力、无标准信封。

这样对比公平，差异纯粹在分发方式。运行时通过 `AGENT_TOOL_MODE` 配置切换注册哪个节点，同一张图结构下对比两种范式。MCP 的优势在于协议标准化和与 LLM 解耦--换 LLM 不影响工具调用层，且每次调用都有标准信封可审计。

### 代码位置
- MCP 版：`app/agents/nodes/ticket_agent.py`（`ticket_agent_node`，Agent 直接调 call_tool）
- FC 版：`app/agents/nodes/ticket_agent_fc.py`（`ticket_agent_fc_node`，LLM 返回 tool_calls）
- FC tools schema：`ticket_agent_fc.py` 的 `_build_tools()`（OpenAI tools 格式）
- 模式切换：`app/agents/graph.py` 的 `build_graph()` 读 `AGENT_TOOL_MODE`

### 面试怎么说
"我们同时实现了 MCP 和 Function Calling 两种工具调用做对比。两者安全层完全一样--槽位收集、双因子校验、工具执行都复用同一套 call_tool 信封入口，差异只在谁决定调工具。MCP 版是 Agent 代码在槽位齐了之后直接调工具，Agent 决定；FC 版是把槽位喂给 LLM 传 tools 参数，让 LLM 返回 tool_calls 再执行，LLM 决定。MCP 的好处是协议化、和 LLM 解耦，换模型不影响工具层，而且每次调用有标准 JSON-RPC 信封可审计；FC 更简单但紧耦合特定 LLM 的 function calling 能力。运行时用 AGENT_TOOL_MODE 配置切换，同一张图对比两种范式，这是面试很好的对比点。"

## 五、PydanticAI 结构化输出

### 技术原理
路由节点和记忆抽取用 PydanticAI Agent 做结构化输出。以路由为例，`output_type=RouterOutput(BaseModel)` 让 PydanticAI 在 SDK 层保证 LLM 返回符合 `RouterOutput` 结构（intent/confidence/sentiment/slots），类型安全，无需手动解析 JSON。

011 之前用 litellm + 4 层 fallback JSON 解析（去 ```` ```json ```` 围栏 → 正则提取 → 修复 → 默认值），代码臃肿且易错--LLM 返回格式不稳定，可能带围栏、可能多返少返字段。改用 PydanticAI 后，SDK 内部做校验和重试，返回的就是强类型 BaseModel 实例，`result.output.intent` 直接用。`run_sync` 同步调用适配 LangGraph 同步 invoke 架构。

### 代码位置
- 路由 Agent：`app/agents/nodes/router.py`（`RouterOutput` + `_router_agent` + `router_node`）
- 记忆抽取 Agent：`app/services/memory_service.py`（`Fact` + `_extract_agent` + `extract_facts`）

### 面试怎么说
"结构化输出我们用 PydanticAI。路由节点要 LLM 同时返回意图、置信度、情绪、槽位四个字段，早期用 litellm 裸调然后手动解析 JSON，写了四层 fallback--去围栏、正则提取、修复、默认值，因为 LLM 返回格式不稳定。后来换成 PydanticAI，定义一个 RouterOutput 的 BaseModel 作为 output_type，SDK 在内部保证 LLM 返回符合这个结构，返回的就是强类型实例，直接 result.output.intent 就能用，不用再手动解析。它内部会校验和重试，类型安全。用 run_sync 同步调用适配我们的同步架构。这是 011 feature 做的迁移，大幅简化了代码。"

## 六、Human-in-the-loop

### 技术原理
转人工用同步标记而非 LangGraph 原生 interrupt/resume。`human_handoff_node` 汇总触发原因（愤怒情绪/敏感操作/低置信度），置 `should_interrupt=True`，agent_service 读到后把会话状态置成 `waiting_human`，等坐席认领。

不用 true interrupt 的原因：项目是同步 invoke 架构，true interrupt 需要 checkpoint 持久化状态 + resume 机制，复杂度高。同步标记 + 会话状态机在 demo 规模下能实现"暂停 AI、等坐席"的效果。转人工触发条件有三层：graph 条件边（路由时判愤怒/敏感/低置信度）、agent_service 轮次转人工（连续 3 轮未解决或累计 15 轮）、注入检测转人工（high 风险注入）。

### 代码位置
- 转人工节点：`app/agents/nodes/human_handoff.py`（`human_handoff_node`）
- 条件边触发：`app/agents/graph.py` 的 `_route_intent()`
- 轮次转人工：`app/services/agent_service.py` 的 `_check_rounds_handoff()`
- 注入转人工：`app/services/agent_service.py` 的 `_detect_injection()`
- 会话状态置 waiting_human：`app/services/agent_service.py` 的 `handle_message()`

### 面试怎么说
"转人工我们用同步标记实现 human-in-the-loop，没用 LangGraph 原生的 interrupt+checkpoint。原因是项目是同步 invoke 架构，true interrupt 需要持久化 checkpoint 再 resume，复杂度高。我们的做法是 human_handoff 节点置一个 should_interrupt 标记，agent_service 读到后把会话状态改成 waiting_human 等坐席认领。转人工有三个触发层：graph 条件边在路由时判愤怒情绪、敏感操作、低置信度；agent_service 在每轮后判轮次--连续 3 轮可解决类意图没解决或累计 15 轮就转人工，知识咨询豁免连续计数因为探索性多轮是正常的；还有注入检测 high 风险直接转人工。这个简化在 demo 规模够用，生产要 true pause/resume 可以加 interrupt_before 加 checkpoint。"

## 七、Prompt 注入检测

### 技术原理
用轻量规则库检测 Prompt 注入，5 条规则覆盖典型手法：忽略指令（ignore_instruction）、角色劫持（role_hijack）、系统提示词泄露（system_prompt_leak）、越狱（jailbreak）、角色扮演（role_play）。中英文双语正则，IGNORECASE。high 规则在前，first-match 即返回，确保 high 命中优先于 medium。

分级处置：high 转人工（不拒绝服务，宪法 IV 兜底，误报可向坐席申诉），medium 放行但标记观察。命中记录 SecurityIncident 表供事后审查。

**为什么不用 ML/LLM 二次判断**：①注入检测必须在主对话前同步完成，加 LLM 二次判断引入延迟和成本；②用 LLM 防 LLM 注入是悖论，判断本身可能被注入绕过；③规则库可解释、可审计、零误判漂移，demo 规模够用；④命中留痕可据此优化规则。

检测在 graph 之前短路：high 风险直接转人工，不进 LLM 决策，防注入输入污染 Agent。

### 代码位置
- 检测规则与逻辑：`app/services/security_service.py`（`_INJECTION_RULES`、`detect_prompt_injection`、`record_incident`）
- 短路集成：`app/services/agent_service.py` 的 `_detect_injection()`
- 事件表：`app/models/security_incident.py`

### 面试怎么说
"注入检测我们用规则库而不是 ML 或 LLM 二次判断。5 条规则覆盖忽略指令、角色劫持、系统提示词泄露、越狱、角色扮演，中英文双语正则。high 级别转人工不拒绝服务，medium 放行标记。为什么不用 LLM 二次判断？三个原因：一是注入检测要在主对话前同步完成，加 LLM 引入延迟成本；二是用 LLM 防 LLM 注入本身是悖论，判断模型也可能被注入绕过；三是规则库可解释可审计、零误判漂移，demo 规模够用，命中留痕还能反哺优化规则。检测放在 graph 之前短路，high 风险直接转人工不进 LLM 决策，防止注入输入污染 Agent 调工具泄露信息。"

## 八、MCP 熔断降级

### 技术原理
经典三态熔断保护工具调用：closed（正常放行）→ open（熔断，直接返回兜底不调工具）→ half_open（放一个探测请求试探恢复）→ closed（恢复）。状态存 Redis 而非内存，因为后端可能多实例部署，内存态各实例独立会导致熔断不一致，Redis 集中存储让所有实例共享同一份状态。

触发：closed 态连续 5 次失败转 open；open 持续 30s 转 half_open 放探测；half_open 连续 3 次成功转 closed 恢复，任一失败立即回 open 重置计时。按 tool_name 隔离，一个工具挂了不影响其他工具。

"失败"的判定不只看异常，还看**关键字段空值监控**：工具返回结果中关键字段（如 ticket_no/status）为空视为结构性故障，计入 fail_count。熔断时返回友好兜底话术 + 转人工（宪法 IV 不拒绝服务）。open 超时转 half_open 放在 `is_broken` 里懒触发，下次调用时顺手检查，不需要后台定时线程。

### 代码位置
- 熔断状态机：`app/core/circuit_breaker.py`（`is_broken`/`record_failure`/`record_success`/`get_state`）
- 集成：`app/services/mcp_service.py` 的 `call_tool()`（is_broken 短路 + `_is_empty_result` 监控）
- 兜底话术：`mcp_service.py` 的 `_fallback_message()`

### 面试怎么说
"工具调用有三态熔断保护：closed 正常、open 熔断、half_open 探测。连续 5 次失败转 open，open 持续 30 秒转 half_open 放一个探测请求，half_open 连续 3 次成功恢复，任一失败立即回 open。状态存 Redis 不存内存，因为多实例部署时内存态各实例独立熔断不一致，Redis 集中存储所有实例共享。失败判定不只看异常，还看关键字段空值监控--工具返回的 ticket_no、status 这种核心字段空了也算故障计入熔断，能在后端持续返脏数据时及时降级。熔断时返回友好话术转人工，不拒绝服务。open 转 half_open 是懒触发放在 is_broken 里，下次有人调用顺手检查超时，不需要后台定时线程。"

## 九、双因子身份校验

### 技术原理
查工单/订单需要双因子：业务编号（ticket_no/order_no）+ 手机号后 4 位。`verify_phone_suffix` 比对终端用户提供的手机号与业务记录绑定手机号的后 4 位。只比对后 4 位是体验与安全的折中--用户在对话里往往只报尾号，要求报全号体验差；后 4 位配合防枚举可接受。

**防枚举核心**：工单不存在、手机号不匹配、未绑定手机号三种情况返回完全相同的 `IdentityVerificationError`（统一消息"未查询到匹配信息"），mcp_service 捕获后统一映射为 -32602。攻击者无法通过不同错误响应判断某个工单号是否存在、某个手机号是否绑定。返回值刻意不含 phone 字段，避免回显绑定手机号。

校验在 MCP server 层（ticket_server/order_server）做，因为它需要查 DB 比对绑定号；mcp_service 层只校验 phone 字段存在。

### 代码位置
- 双因子工具：`app/mcp_servers/base_server.py`（`verify_phone_suffix`、`IdentityVerificationError`）
- 工单校验：`app/mcp_servers/ticket_server.py` 的 `_get_ticket_status()`
- 订单校验：`app/mcp_servers/order_server.py` 的 `_query_order()`
- 统一映射：`app/services/mcp_service.py` 的 `call_tool()`（IdentityVerificationError → -32602）

### 面试怎么说
"查工单订单要双因子校验：业务编号加手机号后 4 位。只比对后 4 位是体验和安全的折中，用户在对话里通常只报尾号。关键是防枚举--工单不存在、手机号不匹配、未绑定这三种情况返回完全一样的错误消息'未查询到匹配信息'，攻击者没法通过不同响应判断工单号是否存在、手机号是否绑定。返回结果也不含 phone 字段，避免回显绑定号。校验放在 MCP server 层做因为它要查 DB 比对绑定号，mcp_service 层只校验 phone 字段存在。这是 OWASP 防枚举的标准做法，把数据存在性和身份匹配两个失败原因合并成一个模糊错误。"

## 十、长期记忆

### 技术原理
跨会话记住用户偏好。三步：①`extract_facts` 用 PydanticAI Agent 从用户消息抽取值得长期记住的事实（套餐/手机号/昵称/偏好），`output_type=list[Fact]` 类型安全；②`save_memory` 把事实向量化存入 Milvus `user_memories` collection，按 tenant+user+fact_type 先删后插实现 upsert（套餐升级覆盖旧值）；③`search_memory` 用当前 query 向量检索相关记忆，相似度 >= 阈值才返回注入上下文。

相似度阈值 0.35（从 0.5 降下来），因为记忆 fact 内容短、表述差异大（用户说"我是高级套餐"vs存的"plan=pro"），0.5 太严会漏召回关键偏好，0.35 提升召回率--记忆场景宁可多召回几条交 LLM 判断，也不要漏掉用户偏好。

全程降级：抽取/保存/检索任一失败都返回空/不抛，记忆是"锦上添花"不能拖垮主对话。

### 代码位置
- 抽取：`app/services/memory_service.py` 的 `extract_facts()`（PydanticAI Agent）
- 保存：`memory_service.py` 的 `save_memory()`（先删后插 upsert）
- 检索：`memory_service.py` 的 `search_memory()`（阈值 0.35）
- 记忆 collection：`app/core/embedding_client.py` 的 `init_memory_collection()`
- 注入与抽取集成：`app/services/agent_service.py` 的 `handle_message()`

### 面试怎么说
"长期记忆让系统跨会话记住用户偏好。用 PydanticAI 从用户消息抽取事实--套餐、手机号、昵称、偏好，向量化存到 Milvus 的 user_memories collection。保存时按 tenant+user+fact_type 先删后插实现 upsert，这样套餐升级能覆盖旧值而不是并存两条。检索用当前 query 向量找相关记忆，相似度阈值我特意从 0.5 降到 0.35，因为记忆 fact 内容短、表述差异大，比如用户说'我是高级套餐'但存的是'plan=pro'，0.5 太严会漏召回，记忆场景宁可多召回几条让 LLM 判断也不要漏掉用户偏好。对话前注入记忆、对话后抽取记忆，全程降级不抛异常，记忆是锦上添花不能拖垮主对话。"

## 十一、全链路可观测（Langfuse）

### 技术原理
两层可观测：Langfuse cloud 做 trace 树（调用层级、耗时），MongoDB 存脱敏明细 trace。

Langfuse 封装的核心是**降级安全**：未配置 key → `get_langfuse` 返回 None → `observe` 返回 no-op 装饰器（原样执行函数，零追踪）。不直接用官方 `@observe` 挂业务函数，而是自封装一层 `observe()`，把初始化推迟到运行时并 try/except 兜底，确保 Langfuse 挂了对话照常跑。

**PII 安全**：`capture_input=False/capture_output=False`，不把原始用户消息（含手机号）传给 Langfuse cloud。Langfuse 只追踪调用层级和耗时，原始 I/O 的脱敏明细存本地 MongoDB trace（`mask_pii` 处理后再写）。

MongoDB trace 拆成 4 步（router/retrieval/agent/generation），每步记录关键字段。TTL 90 天自动过期索引，无需定时清理。每次操作新建 MongoDB client，因为 save_trace 在 daemon 子线程 event loop 跑、查询在主 loop 跑，共享 client 会跨 loop 报 'Event loop is closed'。

### 代码位置
- Langfuse 封装：`app/core/langfuse_client.py`（`get_langfuse` 单例、`observe` 装饰器、`flush`）
- MongoDB trace：`app/services/trace_service.py`（`save_trace`、`_build_steps` 四步、`_ensure_ttl_index`）
- 脱敏：`app/utils/desensitize.py`
- 异步集成：`app/services/agent_service.py`（daemon 线程调 save_trace）

### 面试怎么说
"可观测分两层：Langfuse cloud 做 trace 树看调用层级和耗时，MongoDB 存脱敏明细。Langfuse 封装的核心是降级安全--未配置 key 就返回 None，observe 装饰器变 no-op 原样执行函数零追踪。我没直接用官方 @observe，而是自封装一层把初始化推迟到运行时 try/except 兜底，保证 Langfuse 挂了对话照常跑。PII 安全很关键，capture_input 和 capture_output 都设 False，不把含手机号的原始消息传给 Langfuse cloud，原始 I/O 的脱敏明细存本地 MongoDB。MongoDB trace 拆成 router、retrieval、agent、generation 四步，TTL 90 天自动过期。trace 用 daemon 线程异步写不阻塞响应。"

## 十二、PII 脱敏

### 技术原理
trace 入库前对手机号脱敏，正则 `(?<!\d)1[3-9]\d{9}(?!\d)` 匹配中国大陆手机号，脱敏为 138\*\*\*\*0001 格式（前 3 + \*\*\*\* + 后 4），单向不可逆。

关键是用**数字边界** `(?<!\d)...(?!\d)` 而非 `\b`：Python3 的 `\w` 包含 CJK 字符，中文紧贴手机号时 `\b` 不生效（"号13800001111"中"号"与"1"都是 \w，无词边界），会漏匹配；数字边界只看前后是否非数字，与字符类型无关，中英混排都能正确匹配。前 3 保留运营商号段、后 4 保留尾号便于人工识别，中间 4 位掩码不可逆。

失败 fallback 截断前 20 字而非返回原文--脱敏逻辑本身出错时宁可损失信息也不能把含手机号的原文写进 trace，这是"安全失败"原则。

### 代码位置
- 脱敏函数：`app/utils/desensitize.py`（`mask_pii`、`_PHONE_RE`、`_mask_match`）
- 调用点：`app/services/trace_service.py` 的 `_build_steps()`（slots.phone、query、answer_preview 都过 mask_pii）

### 面试怎么说
"PII 脱敏在 trace 入库前对手机号处理，正则匹配中国大陆手机号脱敏成前 3 后 4 中间星号，单向不可逆。这里有个细节--正则边界用数字边界 `(?<!\d)...(?!\d)` 不用 `\b`，因为 Python3 的 \w 包含中文，手机号紧贴中文时 \b 不生效会漏匹配，数字边界只看前后是不是数字，中英混排都能匹配。脱敏异常时 fallback 截断前 20 字而不是返回原文，宁可丢信息也不能把含手机号的原文写进 trace，这是安全失败原则。脱敏用在 trace 的 slots 手机号、用户查询、回答预览这几个字段。"

## 十三、多租户隔离

### 技术原理
多租户隔离贯穿全栈，是宪法原则 II。tenant_id 来自服务端可信来源（JWT/session），**绝不采信客户端传入值**--mcp_service.call_tool 注入 tenant_id 时覆盖 params 里的客户端值（FR-012）。

隔离体现在各层：
- **MySQL**：所有 CRUD 查询强制 `WHERE tenant_id=?` 过滤
- **Milvus**：tenant_id 作为 partition_key，物理分区裁剪，查询自动带分区过滤
- **ES**：bool query 的 filter 带 `term: tenant_id`
- **Redis**：key 带 tenant_id 前缀（如 `agents:online:{tenant_id}`）
- **会话**：get_by_id 带 tenant_id 过滤，防越权访问他租户会话

中间件链：auth（解析 JWT 拿 tenant_id）→ tenant（注入 tenant_id 到 request.state）→ rate_limit → access_log。auth 必须在 tenant 前，因为 tenant 中间件依赖 auth 解析出的 tenant_id。

### 代码位置
- tenant_id 注入：`app/services/mcp_service.py` 的 `call_tool()`、`app/middlewares/tenant_middleware.py`
- Milvus 分区：`app/core/embedding_client.py`（partition_key=tenant_id）
- ES 过滤：`app/services/retrieval_service.py` 的 `bm25_recall()`
- 会话隔离：`app/services/agent_service.py` 的 `handle_message()`（get_by_id 带 tenant_id）
- 中间件链：`app/main.py` + `app/middlewares/*.py`

### 面试怎么说
"多租户隔离是宪法级原则，贯穿全栈。核心是 tenant_id 只来自服务端 JWT，绝不信客户端--mcp_service 注入 tenant_id 时直接覆盖客户端传的值。隔离体现在每层：MySQL 所有查询带 WHERE tenant_id，Milvus 用 partition_key 物理分区裁剪，ES 用 filter term，Redis key 带 tenant_id 前缀。中间件链 auth 在 tenant 前面，因为 auth 要先解析 JWT 拿到 tenant_id，tenant 中间件才能注入。这样哪怕客户端伪造 tenant_id 也会被服务端值覆盖，彻底防越权访问他租户数据。"

## 十四、幂等设计

### 技术原理
写操作（退款等）用幂等键防重放。`client_request_id` 作为幂等键，Redis SETNX 实现：相同键的重复请求返回首次结果而非重复执行。SETNX 是原子操作，并发请求只有一个能写入成功，其余识别为重复。

退款场景：`request_refund` 必须带 `client_request_id`，order_service 内部 `check_idempotency` 校验，相同键返回首次退款结果。这防止网络重试或用户重复点击导致重复扣款/重复退款--生产事故级防护。

幂等键基础设施独立在 `app/core/idempotency.py`，service 层调用。键带 TTL 自动过期清理。

### 代码位置
- 幂等基础设施：`app/core/idempotency.py`、`app/services/idempotency_service.py`
- 退款幂等：`app/services/order_service.py` 的 `request_refund()` + `check_idempotency()`
- MCP 工具入参：`app/mcp_servers/order_server.py`（request_refund 的 inputSchema 要求 client_request_id）

### 面试怎么说
"写操作用幂等键防重放，尤其退款涉及资金。client_request_id 作为幂等键，用 Redis SETNX 实现--相同键的重复请求返回首次结果而不是重复执行。SETNX 是原子的，并发请求只有一个能写成功，其余识别为重复。退款必须带 client_request_id，order_service 内部校验幂等，这样网络重试或用户狂点都不会重复扣款。这是生产事故级防护，幂等键基础设施独立在 core 层，带 TTL 自动过期。"

## 十五、SSE 流式输出

### 技术原理
业务闭环（010）支持 SSE 流式输出，让用户逐步看到回答而非等全部生成完。Agent 处理结果通过 Server-Sent Events 推流到前端，分阶段输出（路由识别中 → 检索中 → 生成中 → 完成），提升首字响应体验。

SSE 是单向流（服务端→客户端），用 `text/event-stream` Content-Type，比 WebSocket 轻量，适合"服务端推、客户端只读"的客服回答场景。前端 EventSource 接收。

### 代码位置
- SSE 端点：`app/api/v1/agent.py`（流式消息接口）
- 契约测试：`tests/contracts/test_business_streaming.py`

### 面试怎么说
"我们支持 SSE 流式输出，让用户逐步看到回答而不是等全部生成完。Agent 处理分阶段推流--路由中、检索中、生成中、完成，提升首字响应体验。选 SSE 不选 WebSocket 是因为客服回答是服务端推、客户端只读的单向场景，SSE 用 text/event-stream 比 WebSocket 轻量，前端用 EventSource 接收就行。这是 010 业务闭环 feature 做的，有专门的契约测试覆盖。"
