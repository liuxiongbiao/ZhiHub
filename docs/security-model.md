# 安全模型说明

> 更新日期：2026-11-03
> 登录态放在 `Authorization: Bearer` 头里，不放在 Cookie 中。浏览器不会在跨站请求里自动附带这个头，因此当前模型不把浏览器 CSRF 当作可利用攻击面。

## 请求头核对

状态变更请求如果已经带了 Bearer，还必须带上与该 Bearer 完全相同的 `X-CSRF-Token`。缺头、空头、或任意其他字符串都返回 403。

这只是拒绝“随便填一个非空头”。它不是 Cookie 会话下的 CSRF 防护。将来如果把登录态改成 HttpOnly Cookie，必须改成签名双提交，不能沿用“头值等于 Bearer”的比较。

Widget 匿名通道、登录、注册和支付宝回调保持豁免。

## 故障时的取舍

- 登出黑名单查不到：拒绝请求，HTTP 返回 401，WebSocket 关闭连接。已登出的令牌不能在 Redis 故障期间继续使用。
- 登录锁定状态查不到：拒绝登录，返回 503。
- 写请求限流和登录 IP 频率限制查不到：放行。这是有意的可用性选择，避免 Redis 抖动时全站写请求失败。

## 监控

`GET /metrics` 不接受租户 JWT。调用方必须提供与 `PLATFORM_OPS_TOKEN` 一致的 `X-Platform-Token`。令牌未配置时接口拒绝访问。

## 纵深防御清单

- 密码：bcrypt，加上手机号和 IP 两个维度的失败锁定
- 令牌：JWT（HS256 白名单算法 + jti 登出黑名单）
- 租户隔离：`tenant_id` 只从 JWT 注入
- 站内信：定向通知只有收件人可以标已读；`user_id` 为空的全员通知同租户可标
- 注入防护：Prompt 注入规则库 + 前端消息渲染转义
- 密钥：生产环境拒绝代码和 compose 中的默认口令；MongoDB 与 Elasticsearch 地址必须带认证信息
