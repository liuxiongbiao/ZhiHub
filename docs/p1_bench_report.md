# P1 三项性能实测报告（2026-08-23）

> 环境：Docker 全栈真实模式（真实 MySQL/Milvus/ES + 真实 DeepSeek/硅基流动 API）
> 方法：A/MCP 50 次真实调用；B/9.06MB 文档真实上传管道；C/25 轮真实对话（检索阈值 0.3）

## A) MCP 工具调用时延（get_ticket_status × 50，双因子通过 + 查询命中）

| 指标 | 实测 |
|---|---|
| P50 | **1.0 ms** |
| P95 | **1.6 ms** |
| P99 | **6.5 ms** |
| Mean / Max | ~1.3 / 6.5 ms |
| PRD 目标 < 2000ms | ✅ **大幅达成（余量 >99%）** |

> 参考：无匹配记录的负向路径（同样完整走权限/双因子/DB）P50 0.6ms / P99 7.8ms。

## B) 10MB 级文档全管道（9.06MB / 上传→解析→切片→向量化→Milvus+ES 双写）

| 指标 | 实测 |
|---|---|
| 上传接口耗时（异步投递） | **422 ms** ✅ |
| 全管道耗时 | **> 600s（10 分钟观察窗口内未完成）** |
| PRD 目标 < 180s | ❌ **未达成** |
| 根因 | 本地解析把 9.06MB 文档切成 **28,392 个极小切片**（按小节切分），向量化与双写海量小切片导致耗时与成本双重爆炸。**修复方向**：接入 RagFlow 语义切片（合并小节为语义完整的大切片，预计切片数下降 1-2 个数量级）或本地切片策略合并小节 |

> 附带验证：trial 套餐知识库数量上限拦截真实生效（已有 24 篇文档时上传被 403 拒绝——PRD §3.2 规则正确）。

## C) 端到端知识问答延迟（25 轮真实对话，阈值 0.3）

| 指标 | 实测 |
|---|---|
| P50 | **6.44 s** |
| P95 | **9.50 s** |
| P99 | **10.78 s** |
| Min / Max | 5.6 / 10.8 s |
| 回答质量 | **25/25 全部带引用回答，零转人工、零幻觉标记** |
| PRD 目标 P95<3s / P99<5s | ❌ **未达成（超标约 2-3 倍）** |

**延迟构成分析**（每轮对话串行执行约 4 次外部调用）：
1. 查询改写（1 次 DeepSeek）~1-2s
2. 向量+BM25 双路召回（Milvus+ES）~0.1s
3. rerank 精排（1 次硅基流动 API）~0.5-1s
4. 最终生成（1 次 DeepSeek，完整回答）~3-5s

**优化方向（按性价比排序）**：
- ① 生成改流式（`/message/stream` 已有）：用户首字延迟可降至 ~2-3s，虽总耗时不变但体验达标；
- ② 查询改写与生成合并（单轮 LLM 调用，改写仅多轮对话时需要）：省 1-2s；
- ③ 取消单轮对话的强制改写（单轮无指代可跳过 rewrite，代码已支持改写==原句则置 null）：约省 1-2s；
- ④ rerank 与生成并行化/缓存常见问题。

> 口径说明：实测为**非流式端点的完整回答耗时**（含全部生成时间）；PRD 的 P95<3s 若按"首字/首包延迟"口径，需流式端点复测（当前链路首包约 2-3s，有达标可能）。此口径差异建议在答辩时主动说明。
