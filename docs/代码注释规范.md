# 智枢 ZhiHub —— 代码注释规范（Commenting Standard）

> 本文档是项目内**唯一**的注释写作标准，适用于 `backend/`（Python）与 `frontend/`（TypeScript/Vue）的全部源代码、测试、脚本与迁移文件。
> 所有新增或修订代码的注释必须符合本规范；历史代码按本规范逐步对齐。

---

## 1. 总则

1. **语言**：注释与 docstring 一律使用**简体中文**；专有名词（LangGraph、MCP、Redis、SSE 等）保留英文原文，不再翻译。
2. **标点**：中文注释使用全角标点（，。：（）——）；英文专有名词之间的标点保持半角。注释结尾使用句号「。」。
3. **内容原则**：注释解释「**为什么**」与「**业务含义**」，不重复代码字面意思；复杂逻辑必须写清设计动机、约束条件与失败分支。
4. **不改变行为**：注释规范化**绝不修改任何代码逻辑、字符串字面量、日志文案、接口签名或响应结构**；只增删注释与 docstring。
5. **死代码**：
   - `backend/app/`、`frontend/src/` 中**明显废弃**的被注释代码块（整段 `#`/`//` 包裹的旧实现）应删除；
   - `tests/`、`scripts/`、`alembic/` 中**一律不删除**任何被注释代码（可能是有意保留的用例或迁移历史）。
6. **规格引用规范化**：
   - 指向 `docs/specs/` 的特性规格 → 写成 `（规格: docs/specs/007-session-lifecycle-handoff）` 或简写 `（规格 007）`；
   - 指向 PRD 的章节 → 写成 `（PRD §3.4）`；
   - 历史审计批次编号（如 `P0-2`、`P1-9`、`022`、`T20`、`US4` 单独出现）**没有仓库内出处**，必须改写为可读的中文描述；若确需保留溯源，写成 `（审计: P1-9 修复）` 并附一句可读说明。
7. **一致性**：同一文件内的术语、格式必须自洽；区块分隔符、docstring 模板按本规范统一。

## 2. Python 后端规范（`backend/`）

### 2.1 模块头部 docstring

**每个 `.py` 文件（含 `__init__.py`、测试、脚本、迁移）**必须以模块 docstring 开头，模板如下：

```python
"""
<模块路径，如 backend/app/api/v1/session.py>

职责: <一句话职责> —— <关键职责点 1>、<关键职责点 2>、……

[可选：端点概览 —— 仅 API 路由文件]
端点概览:
  POST /                 创建会话                        -> session_service.create_session
  GET  /list             会话列表（分页 + 筛选）          -> session_crud.list_sessions

[可选：核心设计 —— 仅复杂模块]
核心设计:
  - <设计要点与动机>

依赖关系:
  - 上游: <谁调用本模块>
  - 下游: <本模块调用谁>
"""
```

说明：
- 职责行把「做什么」讲透；`端点概览` 必须列出**全部**端点并注明下游调用；
- `核心设计` 用于中间件注册顺序、状态机、分布式锁等**易错设计**，必须写明「为什么」；
- 内容稀少的 `__init__.py` 可缩减为两行 docstring（模块路径 + 职责）。

### 2.2 函数与类 docstring

- **每个公开函数 / 方法**必须有 docstring：单行摘要（结尾句号）起步；复杂函数追加空行后写编号步骤、约束与异常分支：

```python
def leave_message(...):
    """转人工无在线坐席时留言自动建单（category=message）。

    流程:
      1. 校验会话存在且为 waiting_human 状态
      2. 有在线坐席 -> 409（等待认领，无需留言）
      3. 无在线坐席 -> 调 human_service.leave_message_if_no_agent 建留言工单
    """
```

- **每个类**必须有 docstring：一句话职责；领域异常类可单行。
- 简单的单行函数（如 `_get_tenant_id`）允许只写单行 docstring。
- 私有函数 `_xxx` 同样需要 docstring（逻辑越隐蔽越要解释动机）。

### 2.3 行内注释与常量注释

- 行内注释与代码同级缩进，`#` 后空一格，写「为什么」，不写「是什么」；
- 常量定义用行尾注释或分组块注释，说明业务含义与取值来源：

```python
MAX_TOKEN_BUDGET = 4000  # 上下文 token 上限，超则截断历史（PRD §3.4 可配置项）
```

- 区块分隔沿用项目既有风格：`# ─── 区块名 ───`（路由分组、状态机分区、初始化步骤等）。

### 2.4 测试与脚本

- 测试文件：模块 docstring 说明**覆盖范围**；测试类 docstring 说明被测对象；测试方法 docstring 说明「验证什么行为、期望什么结果」（`test_xxx_应/在_情况下` 的中文叙述）；
- 脚本文件：模块 docstring 说明**用途与用法**（命令行示例）；关键步骤写编号注释。

### 2.5 Alembic 迁移文件

- 迁移文件**只增不删**：模块 docstring 说明本次迁移目的；`upgrade()` / `downgrade()` 各加一行 docstring；不重排内容。

## 3. TypeScript / Vue 前端规范（`frontend/`）

### 3.1 文件头部 JSDoc

**每个 `.ts` / `.vue` 文件**必须以头部注释块开头，模板：

```ts
/**
 * src/api/request.ts
 *
 * 职责: <一句话职责> —— <关键职责点>。
 *
 * [可选：数据流]
 * 调用方 -> request.get/post -> 请求拦截器(注入 Bearer) -> FastAPI
 *   -> 响应拦截器 -> 成功返回完整响应 / 失败归一化为 ApiError。
 */
```

- `.vue` 文件的头部注释放在 `<template>` 之前；`<script setup>` 内部不再重复写文件级注释；
- `*.d.ts` 类型声明文件写一句话职责即可。

### 3.2 函数 JSDoc

- `src/api/*` 导出的请求函数必须完整 JSDoc：

```ts
/**
 * 创建新会话。
 * @param endUserId 终端用户 ID。
 * @returns 新会话信息（含 session_id）。
 * @throws {ApiError} 401 未认证 / 403 租户停用。
 */
export function createSession(endUserId: string): Promise<Session> { ... }
```

- `store` / `router` / `utils` 的导出函数：至少写一句话职责；复杂函数补 `@param` / `@returns`。

### 3.3 Vue 组件分区注释

- 组件内按「数据流 → 计算 → 生命周期 → 事件」用统一分隔注释分区：

```ts
// ─── 响应式状态 ───
// ─── 计算属性 ───
// ─── 生命周期 ───
// ─── 事件处理 ───
```

- template 内注释用 `<!-- 说明 -->`，写在关键区块上方，不逐行注释；
- Pinia store 分区：`// ─── state ───`、`// ─── getters ───`、`// ─── actions ───`。

### 3.4 行内注释

- 只写「为什么」（如 `// 401 时先尝试 refresh 再重放原请求，避免用户被登出`）；
- 不保留无意义注释（如 `// 定义变量 a`）。

### 3.5 前端测试（Vitest / Playwright 脚本）

- `.spec.ts` 文件：头部注释说明**被测对象与覆盖场景**；`describe` / `it` 的中文描述保持业务可读；
- `tests/e2e/*.cjs` 脚本：头部注释说明脚本流程与前置条件；**不删除**任何被注释代码。

---

## 4. 禁止事项（所有文件）

1. 禁止修改代码逻辑、变量名、函数签名、模板绑定、日志文案、对外接口；
2. 禁止修改或"润色"用户可见的 UI 文案与 Prompt 模板内容；
3. 禁止删除 `tests/`、`scripts/`、`alembic/` 中被注释掉的代码；
4. 禁止新增无意义的注释（如复述代码的注释）；
5. 禁止遗留半截注释、错别字注释、中英文标点混用；
6. 编辑后必须保证文件语法有效（Python 用 `py_compile` 自检；TS/Vue 小心修改，避免破坏字符串或模板）。

---

## 5. 验收标准（Checklist）

- [ ] 每个文件有统一格式的头部注释；
- [ ] 公开函数/方法均有 docstring 或 JSDoc；
- [ ] 行内注释全部解释「为什么」，无废话注释；
- [ ] 审计批次编号（P0/P1/022/T20/USx）已改写为可读描述或带说明保留；
- [ ] 中文注释全角标点、结尾句号；
- [ ] 语法自检通过（Python `py_compile` / TS 编译无新增报错）。
