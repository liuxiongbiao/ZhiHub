## 0. 总览：工作流是什么

你的项目核心是一张 LangGraph 状态图：**5 个节点（Router、Knowledge、Ticket、Order、Human）+ 1 条条件边 + 4 条终止边**。正常一次请求只经过 **2 个节点**（Router + 四个终点之一），图内没有循环。

节点之间靠一张"任务单"（AgentState，一个 Python 字典）传话：
- Router 在任务单上写：这是什么意图、多大把握、用户什么情绪、提到了哪些编号/手机号
- 条件边读任务单决定：接下来去哪个节点
- 业务节点读任务单上自己需要的信息，干完活把结果写回任务单
- 图结束后，外面的系统从任务单上取"最终回答"返回给用户

四个节点的共同设计原则一句话：**确定性的东西（格式、身份校验、状态翻译）交给代码，不确定性的东西（意图判断、知识生成）交给大模型，但用阈值、证据、人工兜底三层防线控制不确定性。**

## 1. Router 节点（分诊台）

文件：`backend/app/agents/nodes/router.py`（重点看 91 行起的 router_node 与 `_get_router_agent()`）
Prompt：`backend/app/agents/prompts/router.txt`

### 1.1 大白话实现流程

1. 从任务单的"对话记录"里，**从后往前找**，找到用户最新说的那句话。
2. 把最近几句对话整理成一段"对话历史"（为什么要带历史：用户上一轮说"查下我的工单"，这一轮只说"13800000001"，单看这句根本不知道他要干嘛，结合历史才知道他在补手机号）。
3. 把"对话历史 + 用户当前这句话"发给大模型（DeepSeek），要求它按固定格式回答四样东西：
   - **意图**：这是知识问题 / 工单问题 / 订单问题 / 敏感操作（退款投诉等）
   - **置信度**：0 到 1 之间，它对自己判断有多把握
   - **情绪**：正常 / 不满 / 愤怒
   - **槽位**：这句话里有没有提到工单号、订单号、手机号（提到了就提取出来）
4. 大模型返回后，**LangChain 负责检查格式**（function calling 模式）：四个字段是不是都在、类型对不对。
5. 检查通过后，把结果写回任务单（intent / confidence / sentiment / slots）。
6. 如果调用失败（网络断了、超时、格式一直不对）：
   - 不抛异常让整个流程崩掉，而是**写"知识咨询 + 置信度 0.3"**。
   - 为什么是 0.3？因为后面的岔路口规则是"置信度低于 0.4 就转人工"，0.3 < 0.4，所以**只要 Router 失败，流程自动把用户送去人工**——一个数字就完成了安全兜底，不用单独写"失败就转人工"的判断。

### 1.2 它做什么（一句话）
一次模型调用，同时识别"用户要干什么、有多大把握、什么情绪、提到了什么编号"。

### 1.3 为什么这么设计（所以然）

| 问题 | 答案 |
|---|---|
| 为什么"识别"和"分发"分开？ | 单一职责：Router 只负责"这单是干什么的"，"交给谁"由条件边决定。改路由规则只改一处（graph.py 的条件边），Router 的产出还能被轮次统计、Trace、前端展示复用。 |
| 为什么一次调用输出 4 样？ | 省钱省延迟。分开调 3 次模型就多 2 次 LLM 调用；一次结构化输出全拿到。 |
| 为什么用 LangChain 结构化输出不手写 JSON 解析？ | 历史教训：以前用 litellm + 4 层 fallback 解析（去围栏、正则提取、修复残缺、默认值），又臭又易错。LangChain 的 with_structured_output 让 SDK 保证返回结构。 |
| 为什么兜底是"0.3 的知识咨询"？ | 兜底值和阈值是配套设计的：0.3 < 0.4 条件边必然转人工。用数据驱动 fail-safe，不用分支驱动。 |
| 置信度可靠吗？ | **不可靠到可以做统计结论**：模型自己打的 confidence 没有做过统计校准，是"经验阈值"不是校准过的概率。这是要如实说的边界。 |

### 1.4 源码指引（打开代码看哪里）
- 找最后一条用户消息 + 拼对话历史：`router.py` router_node 前半段
- 创建 LangChain 结构化输出链：`router.py` 的 `_get_router_agent()`
- 失败兜底：`router.py` 的 `_fallback_result()`
- 条件边阈值 0.4：`graph.py:181`

### 1.5 老师可能追问
- "LangChain 校验通过就一定对吗？" → 只保证**格式对**（四个字段都在、类型对），不代表**语义对**（可能把工单误判成知识问题）。所以有置信度阈值 + 转人工双保险。
- "置信度是模型自己打的，能信吗？" → 没有统计校准，是经验阈值，0.4 是当前配置值。
- "为什么不用 response_format 的 JSON 模式？" → DeepSeek 不支持 OpenAI 的 json_schema 严格模式（实测 400），所以用 function calling（tools 机制）。

## 2. Knowledge 节点（知识专员）

文件：`backend/app/agents/nodes/knowledge_agent.py`（重点看 123-223 行）
Prompt：`backend/app/agents/prompts/knowledge.txt`

### 2.1 大白话实现流程

1. 从任务单里拿"用户问题"和"租户号"（租户号用来只搜自己企业的知识库，防止搜到别人的）。
2. 拿着问题去知识库检索，这一步内部其实做了好几件事：
   - **先改写问题**：用户问"它支持哪些功能"，如果前面聊过"专业版"，就改写成"专业版支持哪些功能"这种完整问题，否则搜不准。
   - **双路找**：一路去 Milvus（向量库）找"意思相近"的，一路去 Elasticsearch 找"关键词一样"的，各找 20 条。
   - **合并精排**：把两路结果合并去重，交给精排模型（reranker）重新打分，取最相关的 5 条。
   - **低分再试**：如果最相关的第 1 条分数低于 0.6，让大模型先"猜一段假设答案"，再用这段假设答案去搜一次（这叫 HyDE）。还是低于 0.6 → 转人工，**绝不让模型硬编**。
3. 把 5 条片段编号（片段1、片段2……），每条标上来自哪个文档，写进提示词模板。
4. 把提示词发给大模型：**只许根据片段回答，不许编造，回答末尾注明来源**。
5. 三种特殊情况：
   - **一条都没检索到** → 不调用大模型，直接说"暂未找到相关信息"。
   - **大模型生成失败** → 转人工（而且这次回答不算"有效回复"，不计费）。
   - **流式路径** → 图内只检索不生成（skip_generation），真正的逐字输出由图外的流式接口统一做。

### 2.2 它做什么（一句话）
先查企业知识库找证据，再让模型**照着证据**生成带引用的回答，没有证据就明说，不确定就转人工。

### 2.3 为什么这么设计（所以然）

| 问题 | 答案 |
|---|---|
| 为什么必须带来源？ | 企业客服的回答要可追溯、可审计。prompt 强制"末尾注明来源：文档名-片段位置"，来源同时存进 MySQL，前端显示引用气泡。这是 RAG 和自由聊天的本质区别。 |
| 为什么没结果时不调用模型？ | 防幻觉第一道闸：没有证据就不许编。让模型硬答它很可能编造政策，企业客服里这是事故。 |
| 为什么低分转人工不硬答？ | 防幻觉第二道闸：检索到片段但相关性不够，说明库里可能没有真正匹配的答案，照着弱相关片段答容易错。"不确定就不自动决策"。 |
| 为什么温度 0.3、上限 800 token？ | Router 用 0.0 要确定性；知识回答温度 0.3 更自然但不过分发散。800 token 限制长度防啰嗦。 |
| 为什么生成失败也转人工？ | 系统异常时返回的兜底话术不算"有效回复"（不计费、转人工），避免"系统烂了还假装回答了"。 |

### 2.4 源码指引
- 调检索：`knowledge_agent.py:162-169`
- 低分转人工：`knowledge_agent.py:172-178`
- 格式化来源：`knowledge_agent.py:43-68`
- 生成回答：`knowledge_agent.py:71-119`
- 无结果兜底：`knowledge_agent.py:204-207`
- 生成失败转人工：`knowledge_agent.py:212-222`

### 2.5 老师可能追问
- "这个节点调了几次模型？" → 完整路径：改写 1 + Embedding 1 + Rerank 1 + 生成 1；低分时再加 HyDE 的 LLM + Embedding + Rerank。加上 Router 和记忆抽取，一次知识问答最多约 8 次模型相关调用。
- "检索挂了会怎样？" → 异常被捕获置空，返回"暂未找到"，不抛异常、不转人工（除非低置信度）——基础设施挂了也不能让链路崩。

## 3. Ticket 节点（工单专员）

文件：`backend/app/agents/nodes/ticket_agent.py`（重点看 68-172 行）
工具网关：`backend/app/services/mcp_service.py`（call_tool，172-279 行）
工单服务：`backend/app/mcp_servers/ticket_server.py`

### 3.1 大白话实现流程

1. 从任务单的槽位里看 Router 有没有提取到工单号；没有就从用户说的话里找"TK- 开头"的内容。
2. **还没有工单号 → 反问**："请提供您的工单编号（格式 TK-XXXXXXXX）"——这一轮到此为止，**绝对不去查数据**。
3. 找手机号：任务单槽位里有就用，没有就从用户消息里找 11 位数字。
4. **手机号缺失或格式不对 → 反问**："为保护您的账户安全，请提供绑定手机号"——同样不查数据。
5. 两个都有了 → 把"查询工单号 xxx + 手机号 xxx"打包成一张 **JSON-RPC 请求单**，交给守门人（call_tool）。
6. 守门人依次做 9 步检查（全在 mcp_service.py）：
   ① 检查请求单格式对不对 → ② **注入租户号（用系统自己认证的，用户传的租户号一律不信、覆盖掉）** → ③ 检查这个工具存不存在 → ④ 检查当前角色有没有权限调这个工具 → ⑤ 检查这个服务有没有熔断 → ⑥ 检查参数格式（工单号必须 TK- 开头、手机号必须有、长度不超限）→ ⑦ 交给工单服务执行 → ⑧ 检查返回结果的关键字段（工单号、状态）是不是空的 → ⑨ 打包成成功信封返回。
7. 工单服务执行时：按"工单号 + 租户号"查数据库 → **比对手机号后四位**是否匹配。
8. **查不到 / 手机号不匹配 → 返回同一个回答："未查询到匹配信息"**——绝不告诉用户是"单号不存在"还是"手机号不对"（防止有人靠报错区别来试探哪些工单号真实存在）。
9. 查到 → 把英文状态翻译成中文（open→待处理、in_progress→处理中、resolved→已解决、closed→已关闭），**用代码拼成一句话回复**——这一步不叫大模型。

### 3.2 它做什么（一句话）
先收齐"工单号 + 手机号"两个凭证，才允许通过受控工具网关查工单；缺任何一样就反问，绝不裸查。

### 3.3 为什么这么设计（所以然）

| 问题 | 答案 |
|---|---|
| 为什么缺槽位就反问不调工具？ | 两个理由：① 省无效调用——缺手机号去调工具必然失败，先反问让用户补齐下一轮一次成功；② 安全——没验证身份前根本不触发查询，纵深防御第一层。 |
| 为什么"编号 + 手机号后四位"双因子？ | 只用编号，任何人报个号就能查别人的单。加手机号后四位，攻击者要同时知道两者。注意：**这是业务字段组合校验，不是密码学双因素认证**——后四位可猜测、不能证明真实持有，要如实说。 |
| 为什么"不存在"和"不匹配"返回同一个错误？ | 防枚举攻击。如果报错不同，攻击者就能判断某个工单号是否真实存在，从而批量试探。统一"未查询到匹配信息"，把两个失败原因合并成一个模糊错误。 |
| 为什么默认模式不让 LLM 生成回复？ | 查询结果是结构化、确定的。让 LLM 转述它可能"润色"出错误的状态或金额。**确定性业务交给代码模板，不确定性业务才交给 LLM**——这是全项目的分工原则。 |
| 为什么守门人先查"方法存在"再查"权限"？ | 反直觉但符合 JSON-RPC 标准语义：不存在的方法返回"方法不存在"，存在但无权才返回"权限不足"。顺序对了，协议合规；这是细节加分点。 |

### 3.4 源码指引
- 提取工单号：`ticket_agent.py:94-104`
- 缺单号反问：`ticket_agent.py:107-112`
- 缺手机号反问：`ticket_agent.py:120-125`
- 构造信封并调用：`ticket_agent.py:132-136`
- 守门人 9 步：`mcp_service.py:172-279`
- 双因子校验 + 统一错误：`ticket_server.py:152-195`
- 权限矩阵：`mcp_service.py:52-56`

### 3.5 老师可能追问
- "FC 模式和 MCP 模式什么区别？" → MCP：节点代码决定调工具（确定性高）；FC：LLM 看工具清单返回 tool_calls（灵活但多一次模型决策）。**两者最终都进同一个 call_tool 网关，安全规则一样，不会绕过。**
- "怎么防跨租户查单？" → 三层：① 网关用服务端 JWT 的租户号覆盖客户端传入值；② 查询按"单号+租户号"双条件过滤；③ 租户号缺失直接拒绝（fail-closed）。

## 4. Order 节点（订单专员）

文件：`backend/app/agents/nodes/order_agent.py`（重点看 70-185 行）
订单服务：`backend/app/mcp_servers/order_server.py`

### 4.1 大白话实现流程

和工单几乎一样，差异在三点：

1. **找订单号**：任务单槽位里有就用，没有就从消息里找"ORD- 开头"的内容（支持 ORD-DEMO-0003 这种多段格式）。
2. **找手机号**：接受完整 11 位，**也接受独立的 4 位数字**（因为双因子只比对后四位）。有个细节：**先删掉消息里的订单号再找 4 位数字**——防止把"ORD-DEMO-0003"里的 0003 误当成手机号后缀。
3. 缺订单号 → 反问；缺/错手机号 → 反问（同样不调工具）。
4. 双齐 → 打包 JSON-RPC 请求单（query_order）→ 走同一个守门人（call_tool）的 9 步检查 → 订单服务按"订单号+租户号"查库 → 比对手机号后四位 → 查不到/不匹配统一"未查询到匹配信息"。
5. 查到 → **7 种状态翻译成中文**：待支付 / 已支付 / 已发货 / 已完成 / 已取消 / 退款中 / 已退款，加上金额、实付金额；**已发货的订单附带物流单号**。
6. **退款不会在这里发生**：用户说"我要退款"，Router 会把它识别成"敏感操作"，在岔路口（条件边）就转人工了——Order 节点只负责查询，不负责退款。

### 4.2 它做什么（一句话）
和工单同构的"先收凭证再查"流程，查询订单状态、金额、物流。

### 4.3 为什么这么设计（所以然）

| 问题 | 答案 |
|---|---|
| 为什么接受 4 位后缀？ | 用户查订单时通常不想报完整手机号，后四位够校验了（双因子只比后四位）。体验更好。 |
| 为什么先删订单号再找 4 位数字？ | 防止误匹配：订单号 ORD-DEMO-0003 里就含 "0003"，不先删掉会把它当成手机号后缀，导致身份校验错乱。这是真实踩过的坑的修复。 |
| 为什么退款不走这里？ | 退款是写操作 + 资金 + 需要审批人身份。MCP 调用链只有角色和租户号，没有"谁在审批"的审计身份，所以退款走正式 HTTP 端点 + 审批人记录。而且退款意图在 Router 层就被拦去转人工了。 |

### 4.4 源码指引
- 提取订单号：`order_agent.py:97-107`
- 提取手机号（含防误认）：`order_agent.py:39-59`
- 7 态映射：`order_agent.py:160-164`
- 物流单号：`order_agent.py:174-176`

### 4.5 老师可能追问
- "订单有哪些状态？" → 7 态：created（待支付）、paid（已支付）、shipped（已发货）、completed（已完成）、cancelled（已取消）、refunding（退款中）、refunded（已退款）。

## 5. Human 节点与 HITL（人工接管）

文件：`backend/app/agents/nodes/human_handoff.py`（节点本身）
人工闭环：`backend/app/services/human_service.py`（认领/回复/退回/留言）

### 5.1 大白话实现流程

**第一步：节点打标记（图内，很轻）**
1. 从任务单读三样东西：情绪、意图、置信度。
2. 拼出转人工的原因：用户愤怒 / 涉及敏感操作（退款投诉）/ AI 把握不足（可能多个同时命中）。
3. 在任务单上写"should_interrupt = True"（要转人工了），再写一句给用户的提示："您的问题因以下原因已转接人工客服：……"。
4. 图正常走到 END，结束。

**第二步：图外闭环（真正的接管动作都在这里）**

5. 外面的系统（agent_service）看到任务单上"should_interrupt = True" → 把会话状态改成 **waiting_human**（等待人工）→ 通过 WebSocket 通知同租户的在线坐席"有新会话要人工处理"。
6. **坐席认领**：坐席点"认领"，系统执行一条 Redis 原子命令：**"只有没人认领过才允许设置，且 5 分钟自动过期"**。两个坐席同时抢，只有一个能成功（原子性保证）→ 抢到的那个再校验会话状态 → 把会话改成 **human_handling**（人工处理中），记下"是谁认领的" → 广播给其他坐席"这个会话被认领了"，也告诉用户"客服已接入"。
7. **人工回复**：认领的坐席打字发消息 → 系统校验"这个会话确实在人工处理中，且操作者就是认领的那个人" → 以"agent"身份存进消息表 → 通过 WebSocket 实时推给用户。
8. **退回 AI**：认领的坐席点"退回 AI" → 校验确实是认领者本人 → 状态改回 agent_handling、清空认领人、**释放认领锁**、插入一条"正在继续查询"的过渡消息、告诉用户"已转回智能助手"。用户下一条消息会**重新从 Router 开始**跑一遍完整流程。
9. **没有坐席在线**：用户留言 → 系统自动建一张"留言工单"（category=message），消息不丢，坐席上线后可以处理。

### 5.2 它做什么（一句话）
图内节点只负责"判断要不要转人工 + 打标记"，真正的人工闭环（状态管理、防双抢锁、实时通知、回复、退回、留言建单）全部在图外服务层完成。

### 5.3 为什么这么设计（所以然）

| 问题 | 答案 |
|---|---|
| 为什么节点只打标记，闭环在图外？ | 关注点分离：图管"AI 决策"，服务管"业务编排"。状态管理、锁、通知需要数据库/Redis/WebSocket，属于服务层能力，塞进节点里会污染图的纯粹性。 |
| 为什么用 Redis SETNX 不用数据库锁？ | 原子 + 高效。"只有不存在才设置"和"设置"是单条原子命令，并发只有一个成功。数据库实现同样的并发控制要事务+行锁+版本号，慢且复杂。 |
| 为什么锁有 5 分钟 TTL？ | 防死锁：坐席认领后电脑崩了/断网了，锁如果永不过期，会话永远被占着。5 分钟自动释放。但注意：**数据库里的接管状态不会随锁过期自动清除**，完整方案要坐席心跳续租——这是改进项，要如实说。 |
| 为什么回复前校验"是认领者本人"？ | 防越权：谁认领谁负责。其他坐席不能插嘴，退回 AI 也只有认领者能做。 |
| 为什么是"业务层 HITL"而不是 LangGraph 原生 interrupt？ | 项目用同步 graph.invoke，原生 interrupt 需要 checkpoint 持久化 + 断点恢复，复杂度高。项目选择：节点打标记 → 图照常走完 → 图外状态机完成"暂停 AI、等坐席"。效果接近但不是 checkpoint/resume——**退回 AI 后从 Router 重新开始，不是从旧节点恢复**。 |
| waiting_human 阶段为什么还有缺口？ | 拦截校验只覆盖已认领的 human_handling；等待认领的 waiting_human 阶段，用户继续发消息仍可能重新进图改变状态。这是如实存在的缺口，生产改进：等待期新消息只落库推给坐席、不进图。 |

- 认领（SETNX 锁）：`human_service.py:48-130`（核心在第 78 行）

### 5.5 老师可能追问
- "人工退回 AI 后从哪继续？" → 不是 checkpoint 恢复。状态改回 agent_handling 后，下一条消息重新加载上下文和记忆，**从 Router 重新执行**。
- "锁过期了怎么办？" → 锁 5 分钟 TTL 自动释放，但数据库接管状态不会——空闲 30 分钟由清理任务收尾。改进方向：心跳续租或数据库乐观锁作为权威。
- "没有坐席在线怎么办？" → 留言自动建工单，消息不丢。

## 6. 一页总结

| 节点 | 表面做法 | 底层原因（所以然） |
|---|---|---|
| Router | 一次调用输出意图/情绪/置信度/槽位 | 省钱省延迟；兜底 0.3 < 阈值 0.4 = 用数据驱动 fail-safe |
| Knowledge | 检索后带引用回答 | 证据可追溯；无证据不硬答 = 防幻觉两道闸 |
| Ticket/Order | 先收槽位再调工具 | 防无效调用 + 纵深防御；双因子 + 统一错误 = 防越权防枚举 |
| Human/HITL | 节点打标、图外闭环 | 关注点分离；SETNX = 原子防双抢；业务层 HITL ≠ 原生 interrupt |

**贯穿四个节点的总原则**：
> 把"确定性"和"不确定性"严格分开——确定性的（意图格式、身份校验、状态映射）交给代码和协议，让它们快、稳、可审计；不确定性的（意图判断、知识生成）交给大模型，但用置信度阈值、检索证据、人工兜底三道防线控制它的不确定性。
